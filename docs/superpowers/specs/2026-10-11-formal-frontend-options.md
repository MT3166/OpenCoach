# OpenCoach 正式版 H5 技术方案

- 状态：方案及直接记课补充已批准并实现，2026-10-12部署到测试域名；详见 `docs/superpowers/reviews/2026-10-11-formal-h5-acceptance.md`。
- 用户已确认：正式版需要调整前端架构；https://coach.qtedu.ac.cn/ 是测试环境。
- 保留要求：每教练独立部署，学员端优先展示教练姓名或品牌，现有账号与业务数据保留。
- 首发范围：H5 独立交付，小程序作为客户按需选择的后续客户端；技术方案不承诺具体微信平台费用。

## 1. 已确认的前端方向

- Vue 3 + Vite 建立独立前端，正式应用页面由组件与客户端路由管理。
- 手机浏览器与电脑共用 H5，保留教练与学员各自的页面入口。
- 小程序不占用首版交付范围；后续可复用业务 API，客户端界面与认证按平台单独适配。
- 教练自己的姓名或品牌为学员端主要识别，前端从实例配置获取名称。

配套采用 TypeScript 与 Vue Router，前端通过 Django JSON API 使用现有预约、课时和训练业务能力。当前后端业务实现继续作为迁移基础。

## 2. 配套 H5 架构

浏览器中的 Vue 页面负责界面、表单交互和页面导航。Django 提供 JSON API、身份权限、数据查询和业务写入。数据库和业务事务由后端管理。

- 前端：Vue 3、TypeScript、Vite；Vue Router 管理 `/coach/`、`/student/` 等真实页面路由。
- 后端：沿用 Django，增加已获授权的 Django REST Framework，承担 JSON 请求校验、响应序列化和 API 权限适配。
- 状态：首期使用 Vue 的响应式能力管理登录和实例品牌信息，页面从 API 获取业务数据；有明确缓存需求时再引入额外状态或查询库。
- 数据：保留现有模型和 SQLite 事务设计。数据库是否改用 PostgreSQL 独立评估，不以调整前端作为换库依据。
- 部署：继续使用 Docker 和现有 Caddy。Node 用于构建；运行时交付前端静态文件及 Python API 服务。

首期不引入服务端网页渲染框架。正式应用页面由前端组件渲染；前端打包的 index.html 可以作为普通静态文件返回，不需要 Django 模板参与页面内容渲染。

## 3. API 与认证边界

现有页面返回 HTML、跳转和页面消息，除了 `/health/`，尚没有完整业务 JSON 接口。新增 `/api/v1/` 接口层，按已实现能力分组：

1. 当前登录身份、登录、退出、教练实例品牌配置和邀请注册。
2. 教练的学员档案、邀请与课包录入、学员自己的课包查询。
3. 课程发布与查询、预约、取消、完课及缺席处理。
   用户已批准补充直接记课：教练无需提前排课/预约即可记录已上的课，并保留已有预约快捷确认；直接消课需要独立来源、事务与幂等保障。
4. 训练记录、课后计划、学员草稿与正式提交、教练点评。
5. 教练工作台、学员首页、预约与训练列表等聚合查询。

H5 前端与 API 使用同一域名，继续使用 Django Session、HttpOnly/Secure Cookie 和 CSRF；登录、退出和业务写请求均校验 CSRF。会话入口返回前端所需的身份、角色和 CSRF 信息，避免前端硬编码每个实例派生的 Cookie 名称。

后续客户选择小程序时，再确定相应登录方式、客户端会话保存与认证机制。业务接口可复用，本轮不预先加入微信登录、平台 SDK 或小程序特定身份字段。

前端路由守卫用于引导用户，API 自身校验登录、角色和对象归属。学员身份从登录会话推导；创建学员、发布课程、生成邀请和录入课包必须先检查教练权限。

接口约定包括：稳定的错误代码和字段错误、列表分页与日期筛选、时间序列化与上海时区显示、动作字段的数据类型，以及预约和课包录入的唯一操作标识。重试沿用同次操作标识，状态变更和余额以服务端结果为准。

## 4. 现有业务如何复用

- `coaching/accounts.py`：学员创建、邀请签发与邀请注册。
- `coaching/booking.py`：排课、购买录入、课包余额、预约、取消、完课与缺席；保留事务、并发和幂等规则。
- `coaching/training.py`：动作校验、课上记录、课后计划、草稿/提交和点评。
- 当前页面视图中的筛选、看板查询与 HTML 消息需要改为 API 查询、序列化及稳定错误响应。
- 现有服务并非全部自行校验调用者权限；API 层必须补齐角色检查，不能只替换返回格式。

维持一教练一实例的权限边界。现有数据模型不提供共享多教练数据库的租户隔离，本轮方案不增加这一架构。

## 5. 部署选择与建议

首期把前端静态构建产物与 Django API 一起交付到独立应用镜像，继续由已有 Caddy 反代整个教练域名。静态资源由 WhiteNoise 提供，前端入口作为普通文件提供，避免扩大共享商城 Caddy 的挂载和发布范围。

另一种选择是 Caddy 直接托管前端构建产物，并把 API 反代到 Django。静态资源职责更独立，但当前 Caddy 属于已有商城容器，需要增加教练站目录挂载与发布同步；是否采用应作为明确的部署决策。

两种选择均须保证：

- 刷新 `/coach/`、`/student/` 等客户端路由能正常打开应用。
- `/api/` 中不存在的接口返回 JSON 404，不能落入 SPA 入口；缺失静态文件和健康检查也按各自边界处理。
- 上传白名单覆盖前端源码、构建配置和锁文件，并继续保护实例配置与数据库。
- 前端与 API 以匹配版本发布；入口 HTML 与带内容哈希的静态文件采用适合的缓存策略。
- 现有 Caddy 商城站点保留；应用后台仍只在回环地址监听。
- 正式生产实例使用独立配置、数据和账号初始化流程，不自动执行演示数据种子命令。

## 6. 迁移顺序

1. 基于已批准的 Vue 3 + Vite H5、DRF、认证和部署方案，完成可执行迁移计划并锁定兼容依赖版本。
2. 建立 API 层并验证原有业务与对象权限。新增 API 校验和接口测试，保留业务及并发回归。
3. 先迁移登录、品牌信息、教练工作台和学员首页，贯通认证与真实数据读取。
4. 依次迁移排课/预约、课包与完课、训练记录/计划/提交/点评，验证每条完整业务流程。
5. 在测试域名验证手机和电脑、深链接、错误及空状态、数据持久化，再切换正式前端入口。
6. 正式入口接管原有页面地址，确认业务、数据和回滚方式后再退出旧页面实现；HTML 页面测试相应迁移为 API 与浏览器流程测试。

## 7. 已批准的新增依赖及影响

下列为已批准并安装到项目隔离环境的依赖范围，Python精确版本及npm锁文件已记录；未追加UI、状态、HTTP或测试库。新增包仍按用户约定说明用途、影响与替代方案。

| 已批准依赖 | 范围和用途 | 评审时的替代方案 |
| --- | --- | --- |
| `vue`、`vue-router` | 前端界面和页面导航，浏览器运行；安装到项目前端目录 | Vue 已获选型确认；路由也可自行实现，但会增加维护成本 |
| `typescript`、`vite`、`@vitejs/plugin-vue`、`vue-tsc` | 项目内开发和构建、类型检查；作为前端项目开发依赖 | Vue 3 + Vite 已获选型确认；使用纯 JavaScript 可省略 TypeScript/类型检查工具，但失去接口类型检查 |
| `djangorestframework` | 后端 API 的请求校验、序列化、认证和权限适配 | 使用原生 Django JSON 视图与现有 Form，自行维护接口适配和统一响应 |
| Node 构建环境 | 本机已核实 Node 24.18.0、npm 12.0.2，可在本地打包前端；服务器运行阶段不依赖 Node | 本地构建后上传产物；需要在 Docker 构建时打包则另行明确 Node 构建镜像 |

组件样式、额外状态管理、客户端缓存及新增测试工具在界面方案和具体测试需求明确后决定，不提前添加大型组件库。

## 8. 首阶段接口契约

以下契约已随配套方案批准，先贯通登录、实例品牌与两端首页，再扩展完整业务模块。

| 接口 | 用途及权限 |
| --- | --- |
| GET `/api/v1/session/` | 返回当前身份或未登录状态、实例品牌与 CSRF 令牌；匿名响应不包含任何学员业务数据 |
| POST `/api/v1/auth/login/` | 用户名密码登录，校验 CSRF，返回新身份及更新的 CSRF 令牌 |
| POST `/api/v1/auth/logout/` | 校验 CSRF 并退出会话，前端清理身份及私人页面数据 |
| GET `/api/v1/coach/dashboard/` | 教练权限；今日课程、预约人数、学员总数和待点评提交 |
| GET `/api/v1/student/dashboard/` | 学员权限；自己的下一节课、课包、训练和计划摘要 |
| GET `/api/v1/invitations/{token}/` | 有效邀请的注册信息；不返回其他学员数据或邀请摘要 |
| POST `/api/v1/invitations/{token}/accept/` | 邀请注册，校验 CSRF、密码及确认字段；按原有邀请有效期和一次使用规则开户 |

契约与验收要求：

- 成功响应的业务内容放在 `data` 字段；身份中的 `role` 由服务端确定为 `coach` 或 `student`，不接受客户端指定角色。
- 会话响应包含 `user`、`brand`、`csrf_token`；前端以实例的实际品牌名称或教练姓名显示界面，不固定展示平台工作名称。
- 登录后刷新 CSRF 信息，避免继续使用登录前的令牌；登录、退出和邀请注册均不得因为匿名 API 而跳过 CSRF。
- 错误响应提供 `error.code`、`error.message` 和可选的 `error.fields`。未登录、无权访问、对象不存在、字段错误与业务冲突分别使用相应 HTTP 状态，API 不跳转到 HTML 登录页。
- 权限和 CSRF 的拒绝响应也遵守 JSON 契约，包括进入 API 视图之前的 CSRF 失败；与旧页面的错误呈现按入口分别处理。
- 时间使用带时区的 ISO 8601，页面按 Asia/Shanghai 显示。私教和小班钱包均返回 `remaining`、`reserved`、`available`，数值由后端计算。
- 登录、退出或身份失效后，清除旧身份的页面数据，取消或忽略在途请求，避免把上一身份的响应显示给下一身份。
- 校验现有教练和学员能真实登录，两个首页读取实际数据库结果，学员访问教练接口被拒绝，品牌显示符合各实例配置。
- 前端类型检查及打包通过；现有业务和并发回归继续执行，并增加 API 认证、CSRF、角色与响应契约测试。手机和电脑检查按 Impeccable 的有限验收轮次执行。

## 10. 已批准的轻量记课补充

用户已确认习惯目标为教练持续记课和管理学员，并批准直接选学员记课，同时保留预约课程的快捷确认。功能规则见 `docs/superpowers/specs/2026-10-11-coach-interview-requirements.md` 第10节；实施计划新增任务5A并调整记课页面与发布兼容验收。

现有消课流水必须关联预约，现有课程要求精确起止时间。因此直接记课需要追加独立记录及消课来源，记录实际日期，避免为线下课程伪造时段。既有课包计算、SQLite事务设计、账号与业务数据保留。模型变更范围及兼容回退随任务5A验证，不能继续假设整次迁移没有模型变更。

- 部署方式：每位教练独立部署一套系统，当前由用户负责部署；首个测试实例部署到用户提供的服务器。

## 1. 用户与目标

服务健身私教和瑜伽／普拉提自由教练及其已有学员，覆盖一对一和小班课，以及线下上课后的线上训练跟进。

测试版必须能完成：教练邀请学员、录入课包、发布课程；学员预约；教练确认完课、记录训练、布置课后计划；学员提交完成情况；教练文字点评。各操作写入数据库，不以浏览器本地存储或模拟接口代替。

每个部署对应一位教练。代码共用，配置、账号、数据库及备份按部署实例独立。首版付款继续采用现有方式，由教练录入已购买课时。

## 2. 角色、账号与权限

- 教练：通过初始化命令创建首个教练账号，管理该实例的课程、学员、课包、训练和点评。
- 学员：教练创建学员档案并生成邀请链接；学员通过链接设置唯一登录账号和密码，完成档案绑定。
- 邀请：随机令牌、有效期 7 天、仅能使用一次；服务端保存令牌摘要。仅未绑定账号的档案可重新生成邀请，重发时作废同一档案的旧邀请。
- 登录：账号和密码，使用 Django 的密码散列、会话与 CSRF 保护；角色由服务端决定。
- 对象权限：学员只能读写自己的预约和课后训练提交，只能读取自己的课包、课上记录、计划和点评；教练可管理本实例全部学员。
- 访问他人对象统一返回 404，角色不允许的操作返回 403，不向学员暴露他人数据。登录身份的切换必须通过退出、重新登录完成。

首版不接入短信、微信登录或公开注册，邀请入学是唯一学员开户入口。

## 3. 页面与交互

### 3.1 教练端

- 工作台：今日课程、预约人数、待点评的课后训练。
- 排课：按日期查看课程，创建一对一时段或小班，查看报名学员，取消课程。
- 学员：创建档案、生成邀请、查看课包余额与流水、追加已购买课时、查看学员历史记录。
- 训练详情：逐名学员确认完课或处理缺席，填写课上动作数据，创建课后计划，阅读提交并填写点评。

### 3.2 学员端

- 首页：下一节课、私教与小班可约课时、待完成的课后计划。
- 约课：按日期筛选课程，展示时间、地点、类型与剩余名额，预约或查看自己的预约。
- 训练：课上历史记录、课后计划、自己的提交和教练点评。
- 我的：个人预约、两类课包剩余次数与消课记录、退出登录。

页面优先适配手机，电脑可直接用于演示。采用清晰的课程列表、表单和状态提示，重要操作完成后刷新服务端数据。按钮的加载状态辅助避免误操作，最终一致性由服务端保证。

## 4. 课程与预约规则

- 课程包含标题、类型、开始与结束时间、地点、人数上限；结束时间必须晚于开始时间。
- 一对一名额固定为 1；小班人数上限由教练填写，至少为 2。
- 同一教练未取消的课程时间不能重叠；前一节结束时间等于后一节开始时间可以连续排课。
- 预约只接受尚未开始且未取消的课程。有剩余名额、对应类型可约课时足够、学员没有时间冲突时立即确认。
- 同一学员在同一课程中最多有一条未取消的预约；不能预约与自己其他未取消预约时间重叠的课程。取消后可以重新预约尚未开始的课程，重新检查名额、课时与时间冲突，并创建新的预约记录，保留旧取消记录。
- 课程有人预约后，首版通过取消并重新创建调整课程时间或类型，避免已有预约隐式迁移。
- 一次成功预约占用 1 个名额、预占对应课包 1 次课时。
- 剩余名额按人数上限减去未取消的预约数计算；完课或处理缺席保留报名记录，取消才释放名额。
- 小班共享课程信息和名额，每名学员的预约、训练、计划与课时账目独立。

## 5. 课包、取消与完课

### 5.1 两类课时账户

每名学员分别有私教和小班课时账户。教练追加已购买课时，填写正整数次数。每次上课使用对应账户 1 次，不做两类课时兑换。购买录入携带唯一操作标识，重试同一次录入不会重复增加课时。

- 剩余次数 = 累计录入购买次数 - 已消耗次数。
- 可约次数 = 剩余次数 - 当前有效预约预占次数。
- 例如剩余 10 次、预约 2 节时，显示剩余 10 次、可约 8 次。
- 本次测试范围的课包不设置有效期或退款流程。

### 5.2 预约状态

| 当前状态 | 操作 | 最终状态 | 课时变化 |
|---|---|---|---|
| 已预约 | 教练确认完课 | 已完课 | 预占转为消耗 1 次 |
| 已预约 | 学员在取消窗口内取消 | 已取消 | 释放预占 |
| 已预约 | 教练取消预约 | 已取消 | 释放预占 |
| 已预约 | 教练确认缺席且消课 | 缺席已消课 | 预占转为消耗 1 次 |
| 已预约 | 教练确认缺席并免消课 | 缺席免消课 | 释放预占 |

学员可在开课前至少 12 小时自行取消；距开课恰好 12 小时允许取消。之后由教练处理。取消窗口由服务器时间判断。

教练取消整个课程时，释放仍处于已预约状态的名额及课时。已产生完课或缺席消课记录的课程不能整堂取消；教练可处理其中尚未完成的个人预约，已消耗账目保留。

完课或缺席在课程开始后由教练手动确认，小班逐人处理。已完课、已取消或已处理缺席的预约不能再次产生课时变动。反复提交同一操作返回已有结果；对最终状态提交冲突操作返回明确提示。课时消费流水必须关联预约并具有唯一约束。

## 6. 训练记录与课后指导

- 课上记录：教练按学员填写，每项包括动作名，以及适用的组数、次数、重量或时长，可附课程总结。
- 字段：动作名必填；适用字段按动作填写。填写的组数、次数、时长必须为正数，重量允许 0 表示自重；不适用字段为空。
- 课后计划：教练为指定学员填写计划说明、目标日期及动作目标，可关联一次预约。
- 学员提交：每个计划对应一份实际完成动作数据和文字说明；草稿可保存和修改，正式提交后锁定学员编辑、进入待点评状态，提交记录保留。
- 教练点评：针对一次提交填写文字反馈，学员能查看反馈。每次提交保留一条当前点评，教练可修正文字。
- 课上记录由教练填写、学员读取；课后完成数据由所属学员填写，教练读取并点评。

首版采用动作数据和文字指导，不包含动作视频上传或即时聊天。

## 7. 数据结构与一致性

使用 Django ORM 和 SQLite 文件数据库。核心实体如下；不建立跨教练共享租户表。

| 实体 | 责任与关键关系 |
|---|---|
| 用户及学员档案 | 登录身份、角色、档案与账号唯一绑定 |
| 学员邀请 | 绑定档案、令牌摘要、过期时间、使用状态 |
| 课程 | 类型、时间区间、地点、容量、取消状态 |
| 预约 | 关联课程和学员、状态；同一课程与学员的未取消预约唯一；创建操作标识唯一 |
| 课时账户及流水 | 每学员每类型一个账户；购买或消耗流水；购买操作标识与预约消耗分别唯一 |
| 课上训练记录及动作项 | 关联个人预约，记录各动作实际数据 |
| 课后计划及动作目标 | 指定学员，可关联预约，记录目标数据 |
| 课后提交及动作结果 | 关联计划与学员，区分草稿和正式提交 |
| 教练点评 | 关联课后提交，存文字和更新时间 |

名额检查、时间冲突检查、可约课时检查和预约创建在同一数据库写事务中完成；完课状态变更与课时流水写入也在同一事务中完成。SQLite 使用 IMMEDIATE 写事务、WAL 和 20 秒忙等待上限，避免把不支持行锁的 SQLite 当作支持 SELECT FOR UPDATE 的数据库。

预占次数从有效预约推导，消费次数从课时流水推导，避免另外维护易失真的余额缓存。成功预约、取消和消课均提交事务后才返回成功。遇到暂时写竞争时返回可重试提示，不返回虚假的成功结果。

预约创建使用唯一操作标识，网络重试返回原预约；用户取消后再次主动预约使用新操作标识。取消和完课操作绑定具体预约 ID，因此旧取消请求的重试不能取消新预约。

数据库时间使用 UTC，用户界面按 Asia/Shanghai 显示，服务器已有 UTC 时钟与界面时区分开处理。

## 8. 应用结构与错误处理

推荐 Django 5.2 LTS 单体应用，页面采用模板、HTML/CSS 和少量 JavaScript；不需要 Node 构建工具链。Gunicorn 承载远程 HTTP 请求，WhiteNoise 提供收集后的静态资源。

模块按职责分为账号与邀请、排课预约、课时账目、训练指导。业务写操作集中在服务函数中，页面视图负责身份、输入与结果呈现；权限在服务端验证，不能依赖隐藏按钮。

- 非法表单：在对应字段附近显示原因，保留已填写内容。
- 课程满员或课时不足：拒绝预约并更新实际名额或余额。
- 重复提交：返回已有结果；冲突状态明确提示。
- 邀请过期或已使用：提示登录已有账号或联系教练处理。
- 未登录：进入登录页；越权不返回他人的记录。
- 暂时网络错误：提示重试，重试不会重复预约或扣课。
- 提供 /health/ 运维检查，只返回应用与数据库是否可用，不暴露账号和服务器配置。

## 10. 新增依赖、影响与替代方案

以下为拟安装清单，安装和镜像构建在用户批准后进行。兼容范围内的具体补丁版本在实施时锁定。

| 依赖 | 用途 | 安装范围与影响 |
|---|---|---|
| Django 5.2.x | 页面、账号、会话、权限、ORM、迁移和测试 | 本地项目 .venv 与服务器应用镜像 |
| Gunicorn 23.x | Linux 测试服务器 HTTP 应用进程 | 服务器应用镜像，本地 Windows 不运行 Gunicorn |
| WhiteNoise 6.x | 静态资源服务 | 本地项目 .venv 与服务器应用镜像 |
| asgiref、sqlparse、packaging | 上述包的传递依赖 | 随锁定依赖安装到同一隔离环境 |
| tzdata | Windows 所需 IANA 时区数据 | 本地项目 .venv，按平台依赖安装 |
| python:3.12-slim 基础镜像 | 独立应用运行环境 | 拉取并构建新的 Docker 应用镜像，占用服务器镜像存储 |

不修改服务器系统 Python 的包环境，不使用现有业务容器的数据库。测试阶段无需新增 Nginx、Redis、PostgreSQL 或前端 npm 包。

可选替代方案：仅使用 Python 标准库 HTTP 服务和 sqlite3，没有新增框架包，但需要自行实现路由、会话、CSRF、权限和静态资源处理，开发及验证成本更高。推荐采用隔离安装的 Django 方案。

## 11. 验证与演示验收

### 11.1 自动验证

- 邀请令牌过期、重复使用、重发作废，以及未登录和跨学员对象访问。
- 一对一最后一个名额、小班满员、重复报名、教练排课冲突与学员时间冲突。
- 两名学员并发争抢最后一个名额，仅一人成功。
- 同一学员的可约课时为 1 时并发预约两节不同课程，仅一笔成功。
- 预约预占、取消释放、12 小时边界、临近课程拒绝学员自行取消。
- 取消后重新预约保留旧记录；重试旧取消请求不会取消新的预约；重试同次购买录入不会重复加课。
- 并发或重复完课只生成一笔消课流水；缺席消课与免消课结果正确。
- 开课前拒绝完课或确认缺席。
- 小班某名学员完课或取消，不改变其他学员的记录及课时。
- 课上记录、课后计划、提交和点评按身份控制写权限。
- 并发测试使用文件数据库及独立连接，验证真实 SQLite 事务路径。

### 11.2 实际演示

1. 教练登录，创建学员并发送邀请；学员在另一个设备完成注册登录。
2. 教练录入私教、小班课时并发布课程，学员预约，双方看到同一预约与余额变化。
3. 课程开始后，教练确认预约完课，扣课一次，并填写动作记录和课后计划；演示可使用短时长课程或已开始的样例预约。
4. 学员填写计划完成情况并正式提交，教练点评，学员看到反馈。
5. 演示取消预约与释放预占，小班逐人处理，以及重复完课不会再扣课。
6. 重启应用容器，再次登录，预约、课包、训练和反馈均保留。
7. 手机与电脑检查列表、表单、按钮、加载状态及错误提示，保证手机界面无横向溢出。
8. 对测试数据库创建备份，恢复到独立临时实例并验证记录；原测试实例继续保留。
